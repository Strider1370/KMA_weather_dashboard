# Rate Limit And Radar Loop Notes

## 목적

운영 사용자 증가 시 다시 문제가 될 수 있는 항목을 정리한다.
현재는 즉시 수정하지 않고, 차후 확장 시 참고용으로 남긴다.

## 현재 확인된 이슈

### 1. API rate limit은 사용자 -> 서버 요청 기준이다

- 위치: `server.js`
- 현재 기준:
  - `/api/*`만 제한
  - `1분 300회` 초과 시 `429 Too Many Requests`
- `/data/*`는 현재 rate limit 대상에서 제외했다.

중요:
- 이 제한은 KMA API 호출 제한이 아니다.
- 브라우저나 사용자가 우리 서버에 보내는 요청 수를 제한하는 것이다.

### 2. 현재 polling 구조는 사용자 1명당 분당 여러 API를 호출한다

프론트 기본 polling:
- 기본 주기: `30초`
- 호출 대상:
  - `/api/metar`
  - `/api/taf`
  - `/api/warning`
  - `/api/airports`
  - `/api/warning-types`
  - `/api/lightning`

즉 사용자 1명당:
- 30초당 약 6요청
- 1분당 약 12요청

대략적인 위험 구간:
- 같은 IP 기준 약 25명 수준부터 현재 rate limit에 걸릴 수 있다.

주의:
- 회사/학교/기관망처럼 여러 사용자가 NAT 뒤 같은 IP를 공유하면 더 빨리 걸릴 수 있다.
- GCP 프록시/LB 환경에서는 실제 클라이언트 IP 인식이 중요하다.

### 3. 레이더 루프 끊김 원인은 파일 크기보다 캐시/프리로드 쪽이 더 컸다

초기 증상:
- 재생시간 `0.1초`에서 루프가 끊김
- 동시에 `/api/taf -> 429` 발생 가능

원인:
- 레이더 프레임 preload가 없었음
- 시간 고정 프레임에도 캐시 재사용이 잘 안 되는 URL 구조가 있었음
- `/data/*` 요청이 예전에는 rate limit 버킷에 같이 잡힐 수 있었음

현재 반영된 조치:
- `echo_korea_<tm>.png`는 캐시 허용
- 인터랙티브 맵에서 레이더 프레임 preload 추가
- `/data/*`는 rate limit 제외
- `/api/*`만 rate limit 적용
- rate limit 값 `120 -> 300` 상향

## 현재 상태 요약

현재는 다음 상태다:
- 레이더 루프 관련 즉시 문제는 완화됨
- `0.1초` 재생 시에도 이전보다 429 가능성이 줄어듦
- 다만 사용자가 늘면 polling 구조 때문에 API rate limit 문제는 다시 생길 수 있음

## 차후 생길 수 있는 문제

### 1. 사용자 수 증가 시 같은 IP 기준 429 재발 가능

특히 다음 환경에서 위험:
- 같은 사내망에서 여러 명이 동시에 접속
- NAT/shared IP 환경
- GCP 프록시 뒤에서 IP 식별이 부정확한 경우

### 2. polling이 불필요하게 무거움

변경이 거의 없는 데이터도 매 30초마다 다시 요청 중:
- `/api/airports`
- `/api/warning-types`

이 데이터는 초기 1회 로드 후 재사용하는 편이 더 적절하다.

### 3. API 호출 수가 엔드포인트 수에 비례해 증가

현재는 한 번 polling할 때 여러 API를 병렬 호출한다.
사용자 수가 늘수록 요청 수가 빠르게 증가한다.

## 차후 개선 후보

우선순위 순:

1. `airports`, `warning-types`, `alert-defaults`는 초기 1회만 로드
2. polling 대상은 자주 바뀌는 데이터만 유지
3. 필요하면 `/api/dashboard` 같은 통합 엔드포인트 도입
4. 운영 규모가 커지면 인메모리 rate limit 대신 프록시/LB 레벨 정책 검토
5. GCP 환경에서 `X-Forwarded-For` 기준 IP 식별이 기대대로 동작하는지 확인

## 운영 판단 기준

당장은 다음 조건이면 그대로 운영 가능:
- 동시 사용자가 많지 않음
- 같은 IP를 공유하는 사용자가 많지 않음
- 30초 polling 유지

다음 조건이면 개선 작업 우선순위를 올릴 것:
- 429가 다시 관찰됨
- 특정 기관망에서 접속이 많아짐
- 모니터링상 API 요청 수가 빠르게 증가함
